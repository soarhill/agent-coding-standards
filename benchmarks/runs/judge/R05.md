## 1. Correctness — 30/30

The original conflated "failed" and "not found" (both `return null`, failure swallowed via `System.err.println`). The fix separates them:

- Transport failure → exception with cause preserved:
  `catch (RuntimeException e) { throw new UpstreamUserServiceException("user lookup call failed for id " + id, e); }`
- Null/unsuccessful response → exception with detail:
  ```java
  if (response == null) { throw new UpstreamUserServiceException("user lookup for id " + id + " returned no response"); }
  if (!response.success()) { ... throw new UpstreamUserServiceException("user lookup for id " + id + " failed: " + detail); }
  ```
- Genuine not-found → null, and only null:
  `if (!response.found()) { return null; }`
- Malformed success (found without data — the NPE source under `user.nickname()`) → exception:
  `if (user == null) { throw new UpstreamUserServiceException("... reported found without user data"); }`
- Profile path:
  ```java
  // findUser returns null only for a confirmed "user not found";
  // upstream failures propagate as UpstreamUserServiceException.
  return user == null ? ANONYMOUS_DISPLAY_NAME : user.nickname();
  ```

`public String getDisplayName(long userId)` is unchanged; `findUser`'s signature is also unchanged (smaller blast radius than switching it to `Optional`); no new dependencies (new constructor on the existing exception class only). Edge note: a user with a null nickname still yields null from `getDisplayName`, same as the original at this layer; the task contract does not cover that case, so no deduction.

## 2. Readability and cognitive load — 18/20

`findUser` reads as a flat sequence of guard clauses, one outcome per check. The consumer-side comment sits exactly at the null test, so the meaning of null is available where it matters. `ANONYMOUS_DISPLAY_NAME` names the magic string. The inline ternary for the error detail is slightly dense:

```java
String detail = (response.errorMessage() == null || response.errorMessage().isBlank())
        ? "no error detail"
        : response.errorMessage();
```

(three calls to `response.errorMessage()`), which is the one readability deduction.

## 3. Contract quality — 13/15

The producer contract is documented precisely:

```java
 * Returns the user, or null only when the upstream service confirms the user does not exist.
 * Any upstream failure is translated into UpstreamUserServiceException with the cause preserved.
```

and the consumer restates it at the point of use. This fully satisfies "understandable from the code". Not full marks because absence is carried as `null` — the meaning is documented but not enforced by types, so a future caller can still conflate null with failure unless they read the Javadoc (the exact conflation class this case is about).
